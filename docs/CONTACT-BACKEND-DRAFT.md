## 現在の検証画面

- 実データの入力を促さず、架空のサンプルを用意。送信・受付されない旨を見出しとボタンに明記。
- 表示名、架空メール、分類、架空本文、検証用途の確認をクライアント側で検証。
- 必須・空白・メール形式・表示名50文字・メール254文字・本文2,000文字の境界を確認。
- HTMLのformやsubmitボタンは作らず、通信APIも使用しない。CSPの`connect-src 'none'`と`form-action 'none'`を保持。
- 入力値をHTMLへ展開せず、完了メッセージは固定文字列。保存・URLパラメーター・ログへの書込みなし。消去ボタンとページ離脱・復帰時のクリアあり。
- JavaScript無効時はfieldsetを無効のままにして、入力確認を利用できない理由を表示。
- 必須確認チェックは「個人情報方針への同意」ではなく、架空データを使い送信しないことの確認。未施行の法的下書きへの同意を取得したように見せない。

## 構成案とデータ境界

静的サイト → HTTPS受付API → 非公開の保存先／配送キュー → 承認済み担当者の管理画面・通知。

GitHub Pagesは表示のみ。受付APIは別途承認が必要なサーバー側で動作させる。選定する製品名・サービス・DBは未決定。UIだけで成功表示せず、サーバーが受理した結果に基づく状態表示とする。

| ------------------------ | ------------------------------------------------------------------------------------------------------ |
| 氏名・返信先・分類・本文 | 必要性と文字数を承認後に確定。クライアントとサーバー双方で検証し、未知の項目や過大な入力を拒否         |

## API・通知・管理画面の安全要件

- HTTPS、リクエスト本文のサイズ上限、型・長さ・分類の許可リストをサーバー側で検証。ブラウザー側の検証を信用しない。
- 送信先・送信元はサーバー設定から決定し、ユーザー入力で宛先を切替えない。メールヘッダーの改行やHTMLを安全に処理し、通知に機微な本文を含める範囲を審査する。
- レート制限・濫用対策・リクエスト数や容量の上限をサーバー側で実装する。公開ページに秘密のAPIキーを置く方式は使わない。
- CORSはアクセス制御の代替ではない。Cookie認証を利用するAPIにはSameSite等とCSRF対策を設ける。許可オリジンは最小限にする。
- 担当者の認証と案件単位の認可をサーバー側で行う。管理画面・APIとも未認証・権限外・ID改変を拒否。必要に応じ多要素認証、セッション失効、監査を設計する。
- 通信・保存時の保護、権限の最小化、バックアップの保護と復元、秘密情報のローテーションを確認する。
- 二重送信、リトライ、配送失敗、タイムアウトで受付を二重にしたり、未受理なのに受付済みと表示したりしない。通知失敗と保存失敗を区別する。
- 本番送信の停止スイッチと障害時の告知方法を用意する。停止時も入力情報をURLへ退避しない。
- 導入後にCSPは承認されたAPIのホストだけを追加する。`unsafe-inline`・`unsafe-eval`や全宛先許可で解決しない。
